# Workspace

Use this as a normal coding workspace. Write programs, collect data, build training
environments, train models, and install dependencies as needed.

- `baseware.json`: device schemas. Discover and invoke capabilities with `ludens controller list` and `ludens controller <id> --help`, or Python's `ludens_tools.Client`. Pass the declared parameter object with `--args` or the API.
- Python functions compose through normal imports. `@capability` marks sensing or action functions; add `@record` to save a result envelope to the shared timeline. Use task packages and `ludens bench --help` for evaluations; a Shiori-managed Python program can register evidence with `ludens_tools.current_trial()`.
- Each LLM turn (`observe` -> inference -> tool call) has multi-second latency; never rely on turn-by-turn polling for sub-second reaction windows (e.g., fishing bite/splash reels, timed multi-hit combos, or catching moving targets) or repetitive multi-page dialogue/menu loops. Build `@capability` functions for those fast closed-loop `capture/observe -> detect -> act` loops (or structured parsers/macros that save real effort), rather than trivial single-frame pixel checks you can already see in observations. Fast local detectors—such as distinguishing a real bite splash from a nibble or detecting a menu state—need calibration: inspect recorded `.ludens/timeline/` frames from live attempts with your own vision (VLM), label positive/negative `record_id` cases as a concrete test set (`examples`) in `@eval_capability(fn)` in the same module, and iterate with `ludens eval run <id>`. **Do not wait to succeed in live play before building a capability or its eval**: static `.ludens/timeline/` frame lists only test single-step perception and lack generalization for closed-loop control. Instead, in `@eval_capability(fn)`—where `fn` is the capability or its `"python/path.py:func"` ID in the same module—build a lightweight parameterized **surrogate environment** and mount it with `with ludens_tools.eval_env(env):`. The environment intercepts `Client().observe(query)` through `env.observe(query)`—which may itself call `Client().observe()` to pull real `.ludens/timeline/` background frames/crops without recursion—and intercepts `Client().call("controller/...", args)` through `env.call(id, args)`. Advance latent ground-truth state in virtual time (for example, cursor `(row, col)`, bug position/scare radius, or a randomized sequence of fake nibbles followed by a bite window), and grade the capability directly from that ground-truth state across randomized episodes. Eval functions take no required parameters, must have a docstring, and return flat numeric rewards (`{"pass_rate": 1.0}`) or `{"rewards": {...}, "details": {...}, "passed": bool}`; `passed=False` records failure while retaining partial rewards/details so you can iterate until passing. They run offline: `LUDENS_EPOCH`/`BASEWARE_EPOCH` are stripped and `Client().observe()` replays committed `.ludens/timeline/` records. Check `ludens eval list`, run `ludens eval run <id>` (exit 0 = all passing), and read history with `ludens eval history`. If a capability scores well on its test set (`verified`) but fails or misbehaves in live usage, run `ludens eval adapt <id> --reason "<sim-to-real gap>" --record <record-id>` to mark it `adapting`, update the surrogate environment or test set so the eval reproduces the live failure or visual edge case, and iterate on the capability until `ludens eval run <id>` passes again.
- Adaptation uses the eval module's whole-file `evalCodeSHA`, including module-level test cases, not the eval function alone. Any edit to that file (even capability-only edits or comments) releases the gate; a passing rerun is still required. The hash cannot prove that you added the counterexample: update the test set/verifier rather than relying on an incidental source change.
- `perception.py:Perception`: persistent `sample()` samples at `sample_hz` (default 30; tune as needed); mark it with `@capability` and `@record` to retain observations. Load changes with `ludens perception reload`. The loop reads the latest; `observe` / `ludens observe --help` can inspect earlier records or another capability.
- `action.py:Action`: persistent `step()` runs during auto at `step_hz` (default 30); mark it with `@capability`, optionally `@record`. Use `Client.observe()` for history and `ludens action status/reload/stop` for lifecycle. Stop/reload clears current device inputs; step errors stop the loop.
- `skills/<name>/SKILL.md`: reusable methods, with `name` and `description` frontmatter. `memory/current.md`: current state and next steps.
- `.ludens/timeline/`: shared recorded capability results; other components reference them. `logs/`: run and benchmark records. `ludens.json`: launch settings. Organize other files as needed.

Keep the supplied control epoch unchanged; human takeover ends device access.
