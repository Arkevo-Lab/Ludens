# Workspace

Use this as a normal coding workspace. Write programs, collect data, build training
environments, train models, and install dependencies as needed.

- `baseware.json`: device schemas. Discover and invoke capabilities with `ludens controller list` and `ludens controller <id> --help`, or Python's `ludens_tools.Client`. Pass the declared parameter object with `--args` or the API.
- Python functions compose through normal imports. `@capability` marks sensing or action functions; add `@record` to save a result envelope to the shared timeline. Use `@eval_capability` / `@eval_env` and `ludens eval` for capability evaluations.
- Each LLM turn (`observe` -> inference -> tool call) has multi-second latency; never rely on turn-by-turn polling for sub-second reaction windows (e.g., fishing bite/splash reels, timed multi-hit combos, or catching moving targets) or repetitive multi-page dialogue/menu loops. Build `@capability` functions for those fast closed-loop `capture/observe -> detect -> act` loops (or structured parsers/macros that save real effort), rather than trivial single-frame pixel checks you can already see in observations. Treat each closed-loop `@capability` (**Actor** / policy) and its paired `@eval_capability(fn)` + `with ludens_tools.eval_env(env):` (**Critic** / surrogate world model) as a **co-evolving pair**—neither the policy nor the surrogate environment will be realistic on the first try:
  1. **Bootstrap a minimal `v0` Actor + Critic and probe live**: do not wait for a lucky live success, and do not over-engineer synthetic pixel physics from a single screenshot. Build a minimal `v0` `@capability` and a parameterized `v0` `eval_env` (which intercepts `Client().observe(query)` via `env.observe(query)` and `Client().call("controller/...", args)` via `env.call(id, args)`, advancing latent ground-truth state in virtual time and grading from that ground truth across randomized episodes). Run a live attempt wrapped in `with ludens_tools.record_window() as win:` (or a `@record @capability` probe) while 30 Hz `Perception.sample` records the full trajectory into `.ludens/timeline/`.
  2. **Slice the 30 Hz replay and upgrade the Critic (`eval_env`) first**: pull the multi-second trajectory with `Client().replay(win)` or `Client().replay(around=record_id, before_seconds=2.0, after_seconds=2.0)` (which automatically paginates `.ludens/timeline/` and can also be called inside `env.observe()` without recursion). Inspect the 30 Hz frame sequence to measure real transition timing, motion signatures, and background distractors (e.g., water ripples, fake nibbles, dialogue transitions). Upgrade `eval_env`—by replaying real 30 Hz timeline slices, compositing real crops, or calibrating multi-frame dynamics and negative distractors—until the Critic reproduces the real environment's failure mode and causes naive policies to fail (`passed=False`).
  3. **Iterate the Actor offline, then validate live**: refine the `@capability` against the upgraded Critic with `ludens eval run <id>` until it passes (`verified`), then test in live play. Whenever a `verified` capability fails or misbehaves in live usage, run `ludens eval adapt <id> --reason "<sim-to-real gap>" --record <record-id>` to mark it `adapting`, slice the new replay to upgrade the Critic (`eval_env`) first so it reproduces the failure, and iterate the Actor until `ludens eval run <id>` passes again. Eval functions take no required parameters, must have a docstring, and return flat numeric rewards (`{"pass_rate": 1.0}`) or `{"rewards": {...}, "details": {...}, "passed": bool}`; `passed=False` records failure while retaining partial rewards/details. Check `ludens eval list`, run `ludens eval run <id>` (exit 0 = all passing), and read history with `ludens eval history`.
- Adaptation uses the eval module's whole-file `evalCodeSHA` (and the bound `@eval_env` module's `envCodeSHA` when the eval binds `@eval_capability(fn, env=MyEnv)`), including module-level test cases, not the eval function alone. Any edit to either file (even capability-only edits or comments) releases the gate; a passing rerun is still required. The hash cannot prove that you added the counterexample: update the test set/verifier rather than relying on an incidental source change. Declare reusable surrogate environments with `@eval_env` (a docstring is required; use them as `with MyEnv(...) as env:` or `with eval_env(env):` for ad-hoc stubs) and bind them via `@eval_capability(fn, env=MyEnv)` or `env="python/envs.py:MyEnv"`.
- `perception.py:Perception`: the unified resident perception-and-action state machine; persistent `sample()` is scheduled continuously by the runtime (default 30 Hz ceiling; slow samples backpressure without overlapping or queuing, and video segments compress/evict automatically — never add `sleep` throttling inside `sample()`); mark it with `@observe`, `@capability`, and `@record` to select the main observation channel and retain observations. Capabilities in the continuous state machine can return optional `effect` and `transition` fields to drive in-process closed-loop control and state transitions while sharing instance/module context; inspect or trigger live state transitions without reloading via `ludens perception state` and `ludens perception transition <target> [--args '<JSON>']` (or `Client().state()` / `Client().transition(to, args)`). Edits to `perception.py` or its imported workspace `.py` modules automatically reload the resident process. The loop reads the latest; `observe` / `ludens observe --help` can inspect earlier records or another capability.
- `skills/<name>/SKILL.md`: reusable methods, with `name` and `description` frontmatter. `memory/current.md`: current state and next steps.
- `.ludens/timeline/`: shared recorded capability results; other components reference them. `logs/`: run records. `ludens.json`: launch settings. Organize other files as needed.

Keep the supplied control epoch unchanged; human takeover ends device access.
