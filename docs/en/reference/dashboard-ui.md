# Dashboard UI

The Dashboard uses the Next.js App Router, React, Tailwind CSS 4, and shadcn/ui (Radix / New York). The web page and the optional Electron desktop client share the same components; you do not need to start Electron to develop the UI.

## Component Ownership

- `app/components/ui/` holds component sources introduced via the official shadcn CLI. Buttons, forms, switches, checkboxes, radio groups, sliders, cards, tables, dialogs, feedback, and in-page tabs should reuse these primitives.
- Feature components still live in `components/`; the run timeline, activity evidence, charts, and pet animations are implemented by feature components — never add workspace or Ludens calls into the UI primitives.
- Class-name merging uses `import { cn } from "cn"`, variants use `class-variance-authority`; both stay consistent with the sources generated by the current shadcn registry.

`components.json` records the registry style and paths. To add a new component, run it from the Dashboard directory, for example:

```bash
cd app
npx shadcn@4.23.0 add dialog
```

Only add components currently in use. After generation, review the sources and lockfile; do not use `--overwrite` to clobber local modifications. Current local adjustments include `NativeSelect.wrapperClassName` (controls the wrapper width) and the Slider passing the accessible name and description through to the actually focusable Thumb. Cards use compact defaults (20px padding, 16px section gaps, and 13px descriptions) suited to the console.

## Theming and Styling

`app/globals.css` imports Tailwind and `tw-animate-css`, mapping the existing Ludens dark palette onto semantic tokens via `@theme inline`. The root layout is pinned to `dark`; there is currently no theme-switching feature.

| Purpose | Recommended classes |
| --- | --- |
| Page and primary text | `bg-background text-foreground` |
| Cards and overlays | `bg-card` / `bg-popover` |
| Primary action | Button default variant, using the `primary` gold |
| Secondary actions and weak backgrounds | Button `secondary` / `outline` / `ghost`; `bg-muted` |
| Descriptions and status | `text-muted-foreground` / `text-success` / `text-destructive` |
| Borders, keyboard focus | `border-border` / `ring-ring` |

Note that `--muted` denotes a weak background, while text uses `--muted-foreground`. Existing domain CSS lives in `@layer components`, allowing the Tailwind `utilities` layer to override it; do not add new unlayered global `button` / `input` / `select` styles, or they will override the shared controls' state, size, and focus styles.

Workspace management, settings, Capabilities, Docs, Activity Feed, request details, replay controls, and Loop Lab use the shared primitives. Keep domain geometry (timeline marks, charts, evidence rows, and media) in feature CSS; use theme tokens for surrounding surfaces and status colors.

The visual baseline is a warm charcoal canvas with restrained gold actions, quiet borders, and consistent card spacing. Settings puts console preferences first. Pet following separates the saved workspace from the observed desktop state. This window’s optional desktop controls have their own availability section, and desktop preference cards use two columns from 1100px; narrower screens use one column. Keep related controls together, allow translated labels to wrap, and verify real English and Chinese pages at desktop and narrow widths when adapting a generated design concept.

On Live, Replay and run analysis, an explicit workspace-list retry keeps its button focusable while reading and rejects repeated activation. A failed read leaves the retry available; after successful recovery removes it, focus moves to the main content only if the original focused retry still owns that intent. Moving focus, using the pointer elsewhere or changing the URL cancels restoration. Automatic catalog polling never creates a focus-restoration request, and catalog recovery remains separate from retrying run data.

The UI applies these receipts before independently refreshing the catalog; read retries do not repeat writes. Undo uses the returned path, never a stale list row. Before unregistering, the shared CLI/Dashboard operation clears only a pet target pointing to that workspace. Replay event search reads the entire selected run or cycle through the server's existing archive index. It matches literal, case-insensitive titles, statuses, event types, and identifiers, with an optional track filter; it does not search arbitrary payloads or expand artifacts. Each response scans at most 500 event candidates and returns at most 100 matches. Finishing that snapshot is distinct from indexing the whole archive; only both `scan.complete` and `coverage.complete` justify an exhaustive result or a definitive empty state.

## Interaction Conventions

- Associate form controls with a `Label`, and help text via `aria-describedby`. Icon buttons must have an accessible name.
- Dialogs must have a title and description, focus the first useful input, restore focus to the opener on cancel, and focus the result after a successful creation. Keep in-progress creation visible instead of allowing an accidental dismissal.
- Give buttons an explicit `type`; use `submit` for the submit button of a native form and `button` for everything else.
- `NativeSelect` keeps native option, empty-value, and keyboard behavior; use `Switch` for discrete toggles and `Slider` for numeric ranges.
- Request-detail tabs use the shared `Tabs` primitive for Arrow, Home, and End navigation; inactive panels remain unmounted.
- Whole-row evidence and timeline hit targets may keep native buttons with explicit types and visible keyboard focus. The replay seek bar keeps its native range to preserve continuous millisecond seeking and URL commits on pointer/key release; hidden sound-file inputs remain native.
- Sliders with backend writes update the local value on `onValueChange` and persist on `onValueCommit`, avoiding request storms while dragging.
- Feature requests, pending states, error feedback, and desktop-capability detection are owned by the page; UI primitives handle only presentation and interaction.

Acceptance uses `npm run typecheck`, `npm test`, and `npm run build`, plus checking pages and form actions under an isolated `LUDENS_HOME`. See [Console Debugging and Verification](../tutorials/debugging-and-verification.md).

## Brand Mark

The Ludens mark is a 5 × 5 pixel ring around a hollow L, with one loose pixel at the top right. The ring takes the surface's text color; the loose pixel is always the accent orange (`#ff4f1f`, `--gold`). Keep the pixels square: no rounding, shadow, outline or rotation.

### Motion

The mark's parts carry the console's motion. Everything moves on the pixel grid, in steps: one timing token (`--step`, 60ms), `steps()` easing only, transform and opacity only. The global reduced-motion rule turns all of it off.

`PixelMark` (`app/components/ui/pixel-mark.tsx`) draws the mark; `app/app/pixel-motion.css` holds the token and keyframes.

| Prop | Effect |
| --- | --- |
| `state` | The loose pixel as a status light: `idle`, `reasoning` (pulse), `recording` (blink), `passed` (green), `failed` (red, with a shake), `waiting` (grey, slow blink) |
| `loading` | A three-pixel tail runs round the ring |
| `filled` | The hollow L fills cell by cell in blue: a human holds control |
| `assemble` | The ring drops in clockwise and the loose pixel lands, once on mount |
| `label` | Accessible name; without it the mark is decorative |

At rest the ring is one outline. It splits into thirteen separate cells only while `loading` or `assemble` is set. Hovering or focusing the sidebar brand makes the loose pixel hop once.

In the console shell:

- **Sidebar cursor.** Above 680px an orange pixel marks the active navigation link and steps to a newly selected one in four jumps. Its position is measured from the active link, so it follows scrolling and resizing without the stepped travel. At 680px and below the menu keeps its static underline.
- **Loader.** Waiting states that are not a refresh action use `<PixelMark loading />` instead of a circular spinner. Refresh buttons keep their rotating arrow.
- **Assemble.** The sidebar brand assembles once per browser session, tracked by the `ludens:brand-assembled` session key.

On Live:

- **Status pixel.** The status pill carries a `PixelMark` in place of a round dot. It pulses while Shiori is reasoning or consolidating, blinks grey on standby, and holds steady otherwise.
- **Control handoff.** While a human holds control (host online, manual mode) the mark is `filled`: the hollow L and the loose pixel turn blue, filling cell by cell on takeover and draining on release.
- **Budget blocks.** The run budget bar is 24 blocks. Elapsed blocks are lit and the leading one is orange. It keeps `role="progressbar"` with the same 0–100 values.

Elsewhere:

- **Eval runs.** The run-eval and run-all buttons on Capabilities show `<PixelMark loading />` while an eval runs.
- **Status pixels.** Status indicators are square, matching the mark's loose pixel: the shell and capability status dots, eval status badges, notices, session dividers, replay track markers and source markers. The Live thinking indicator is an orange pixel with the stepped pulse. Chart series markers stay round.
